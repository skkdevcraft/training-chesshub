Create the `FriendRequest` entity to model the friend-request workflow: pending, accepted, rejected.

## What to build

In `ChessHub.Domain`:

- Create `FriendRequestStatus` enum: `Pending`, `Accepted`, `Rejected`
- Create `FriendRequest` entity:
  - `Id` (Guid)
  - `SenderId` (string, FK to User)
  - `ReceiverId` (string, FK to User)
  - `Status` (FriendRequestStatus, default `Pending`)
  - `CreatedAt` (DateTime)
  - `ResolvedAt` (DateTime, nullable — set when accepted/rejected)
  - Navigation properties: `Sender` (User), `Receiver` (User)

In `ChessHub.Data`:

- Add `DbSet<FriendRequest>` to `AppDbContext`
- Configure relationships (two FKs to User — sender and receiver)
- Add a unique constraint or composite index on `(SenderId, ReceiverId)` where `Status = Pending` to prevent duplicate pending requests
- Run migration

## Acceptance criteria

- [ ] `FriendRequestStatus` enum with Pending, Accepted, Rejected
- [ ] `FriendRequest` entity with all fields
- [ ] Two FK relationships to User configured correctly
- [ ] Migration creates `FriendRequests` table
- [ ] Duplicate pending requests are prevented at the database level
